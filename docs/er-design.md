# เอกสารออกแบบฐานข้อมูล

**โครงงาน:** ระบบบริหารงบประมาณการจัดซื้อ ค่านายหน้า และค่าใช้จ่ายแฝง สำหรับธุรกิจตัวแทนจำหน่ายรถจักรยานยนต์
**รายวิชา:** CE396 การออกแบบระบบฐานข้อมูล · DBMS: PostgreSQL 16

---

## 1. สถานการณ์และปัญหา

ตัวแทนจำหน่ายรถจักรยานยนต์หลายสาขาจัดซื้อรถเข้าสต็อกเป็นล็อตตามงบประมาณรายไตรมาส แล้วขายผ่านพนักงานขายที่ได้ค่านายหน้าเป็นเปอร์เซ็นต์ ปัญหาที่เกิดซ้ำคือ

1. **กำไรบนกระดาษไม่ตรงกับกำไรจริง** — ราคาขายลบราคาซื้อดูดี แต่ยังไม่หักค่าขนส่ง ค่าเตรียมรถ (PDI) ค่าจดทะเบียน ดอกเบี้ยสินเชื่อสต็อก ซึ่งเป็น *ค่าใช้จ่ายแฝง* ที่กระจายอยู่ในเอกสารคนละชุด
2. **คุมงบไม่ได้รายหมวด** — งบจัดซื้อ ค่านายหน้า และค่าใช้จ่ายแฝง ถูกจัดสรรแยกกัน แต่ยอดใช้จริงกระจายอยู่คนละที่ จึงตอบไม่ได้ว่าสาขาไหนใช้งบหมวดใดเกิน
3. **ค่านายหน้าแบ่งกันหลายคนในดีลเดียว** — ผู้ปิดการขาย ผู้ช่วย และผู้แนะนำลูกค้า ทำให้เก็บแบบคอลัมน์เดียวในตารางการขายไม่ได้

ขอบเขต: ระบบนี้เก็บข้อมูลเพื่อ **วิเคราะห์ต้นทุนและงบประมาณ** ไม่ครอบคลุมบัญชีแยกประเภท การซ่อมบำรุงหลังการขาย และไม่พัฒนาแอปพลิเคชัน

## 3. ความสัมพันธ์และการตัดสินใจออกแบบ

### 3.1 ความสัมพันธ์ M:N (มี 3 จุด — เกินเกณฑ์ขั้นต่ำ 1 คู่)

| ความสัมพันธ์ | ตารางเชื่อม | แอตทริบิวต์ของความสัมพันธ์ |
|---|---|---|
| สาขา × รอบงบ × หมวด | `budget_allocation` | `amount_allocated`, `approved_by` |
| การขาย × พนักงานขาย | `sale_commission` | `role_in_deal`, `commission_pct`, `commission_amount` |
| คันรถ × หมวดค่าใช้จ่าย | `hidden_cost` | `cost_date`, `amount`, `reference_no` |

`sale_commission` คือเหตุผลหลักที่ต้องแยกตาราง — ถ้าเก็บ `salesperson_id` กับ `commission_amount` ไว้ในตาราง `sale` โดยตรง จะรองรับได้แค่คนเดียวต่อดีล พอมีผู้ช่วยหรือผู้แนะนำก็ต้องเพิ่มคอลัมน์ `salesperson_id2`, `salesperson_id3` ซึ่งเป็นกลุ่มซ้ำ (repeating group) ผิด 1NF ทันที

### 3.2 เอนทิตีอ่อน

`purchase_order_item` ไม่มีความหมายถ้าไม่มีใบสั่งซื้อ จึงใช้คีย์หลักประกอบ `(po_id, line_no)` โดย `line_no` เป็นคีย์บางส่วน — ซ้ำข้ามใบได้ แต่ห้ามซ้ำในใบเดียวกัน และใช้ `ON DELETE CASCADE` เพราะลบใบสั่งซื้อแล้วรายการย่อยต้องหายตาม

### 3.3 ความสัมพันธ์ 1:1

รถหนึ่งคันขายได้ครั้งเดียว จึงวาง `unit_id` ไว้ใน `sale` แล้วประกาศ **`NOT NULL`** + **`CONSTRAINT uq_sale_unit_id UNIQUE (unit_id)`** — UNIQUE คือสิ่งที่เปลี่ยน 1:M ให้เป็น 1:1 จริง ถ้าลืมใส่ ฐานข้อมูลจะยอมให้ขายรถคันเดียวกันสองใบ

### 3.4 คีย์นอกแบบประกอบ

`vehicle_unit` อ้าง `(po_id, line_no)` กลับไปที่ `purchase_order_item` ทำให้รถทุกคัน **สืบย้อนไปถึงราคาซื้อจริงของตัวเอง** ได้ ไม่ต้องเดาจากต้นทุนมาตรฐานของรุ่น นี่คือจุดที่ทำให้คำนวณกำไรรายคันได้แม่นยำ

### 3.5 ตารางเลือก ON DELETE

| คีย์นอก | ตัวเลือก | เหตุผลเชิงธุรกิจ |
|---|---|---|
| `purchase_order_item → purchase_order` | CASCADE | รายการย่อยไม่มีชีวิตของตัวเอง |
| `sale_commission → sale` | CASCADE | ยกเลิกการขาย = คอมมิชชันของดีลนั้นหมดความหมาย |
| `hidden_cost → vehicle_unit` | CASCADE | ค่าใช้จ่ายแฝงผูกกับคันรถโดยตรง |
| `sale_commission → salesperson` | RESTRICT | ห้ามลบพนักงานที่ยังมีประวัติค่านายหน้าค้างจ่าย |
| `vehicle_unit → purchase_order_item` | RESTRICT | รถเป็นทรัพย์สิน ต้องมีที่มาเสมอ |
| `budget_allocation → branch/period/category` | RESTRICT | ข้อมูลอ้างอิงหลัก ลบทิ้งไม่ได้เมื่อมีงบผูกอยู่ |
| `customer_phone → customer` | CASCADE | เบอร์โทรไม่มีความหมายเมื่อไม่มีเจ้าของ (เพิ่มใน v2) |
| `sale → customer / vehicle_unit / branch / period` | RESTRICT | การขายเป็นเอกสารทางบัญชี ห้ามลบลูกค้าหรือรถที่เคยขายแล้ว |
| `purchase_order → branch / supplier / period` | RESTRICT | ใบสั่งซื้อเป็นเอกสาร ต้องอ้างผู้จำหน่ายและสาขาได้เสมอ |

แพตเทิร์นเดียวกับที่เรียนในสัปดาห์ที่ 4: เอกสาร/ประวัติ → RESTRICT · ส่วนเกินของแม่ → CASCADE · ไม่มีความสัมพันธ์แบบเลือกได้ในระบบนี้จึงไม่ใช้ SET NULL
รวมคีย์นอก 20 เส้น (CASCADE 4 · RESTRICT 16) — ตรวจจากระบบจริงได้ด้วย `sql/04-verify.sql` ตรวจ 2

### 3.6 ข้อกำหนด CHECK ที่สำคัญ

- `ck_period_daterange` — วันสิ้นสุดรอบงบต้องมากกว่าวันเริ่ม
- `ck_model_price` — ราคาขายแนะนำห้ามต่ำกว่าต้นทุนมาตรฐาน
- `ck_poitem_discount` — ส่วนลดห้ามเกินมูลค่ารวมของบรรทัดนั้น
- `ck_commission_pct` — อัตราค่านายหน้าอยู่ในช่วง 0–20%
- `ck_supplier_taxid` — เลขประจำตัวผู้เสียภาษี 13 หลักด้วย regular expression

ทุกข้อกำหนดตั้งชื่อเองตามแนวปฏิบัติของรายวิชา (`pk_`, `fk_`, `uq_`, `ck_` และดัชนี `ix_`) — v2 เปลี่ยน PRIMARY KEY / UNIQUE ที่เคยประกาศแบบ inline ให้มีชื่อทั้งหมด เพื่อให้ข้อความ error อ่านออกและเขียน `DROP CONSTRAINT` ได้ถูกตัว

## 4. การทำให้เป็นบรรทัดฐาน (สัปดาห์ที่ 5–6)

โครงสร้างชุดนี้ผ่านการทวนสอบถึงระดับ **BCNF** ทุกตาราง ขั้นตอนที่ทำและสิ่งที่แก้ไป

### 4.1 ระดับ 1NF — กำจัดกลุ่มซ้ำ

| ปัญหาในฉบับร่างแรก | การแก้ไข |
|---|---|
| ตาราง `sale` มี `salesperson_id1`, `salesperson_id2` เพื่อรองรับดีลที่แบ่งคอมมิชชันหลายคน | แยกเป็นตาราง `sale_commission` (M:N) เพิ่มคนได้ไม่จำกัดโดยไม่ต้องเพิ่มคอลัมน์ |
| ตาราง `vehicle_unit` มีคอลัมน์ `freight_cost`, `pdi_cost`, `registration_cost`, `interest_cost` | แยกเป็น `hidden_cost` + `expense_category` เพิ่มหมวดค่าใช้จ่ายใหม่ได้โดยไม่ต้อง ALTER TABLE |

### 4.2 ระดับ 2NF — กำจัดการขึ้นต่อกันบางส่วน

ตารางที่มีคีย์หลักประกอบมี 2 ตาราง จึงต้องตรวจเฉพาะสองตารางนี้

- `purchase_order_item` — PK = (po_id, line_no) เดิมเคยเก็บ `brand`, `model_name` ไว้ด้วย ซึ่งขึ้นกับ `model_id` เท่านั้น ไม่ได้ขึ้นกับคีย์ทั้งชุด → ย้ายไป `motorcycle_model` เหลือไว้แค่ `model_id`
- `sale_commission` — PK = (sale_id, salesperson_id) เดิมเคยเก็บ `full_name` ซึ่งขึ้นกับ `salesperson_id` เพียงส่วนเดียวของคีย์ → ย้ายไป `salesperson`

### 4.3 ระดับ 3NF — กำจัดการขึ้นต่อกันแบบส่งผ่าน

- `purchase_order` เดิมเก็บ `supplier_name` และ `branch_name` ทั้งที่ `po_id → supplier_id → supplier_name` เป็นการส่งผ่าน → เหลือเฉพาะคีย์นอก
- `sale` เดิมเก็บ `customer_phone` ซึ่งขึ้นกับ `customer_id` → ตัดออก
- **`sale_commission.commission_amount` เก็บแม้คำนวณได้จาก `commission_pct × sale_price`** — เพราะเป็นยอดเงินที่จ่ายจริงแล้ว (ข้อเท็จจริงทางการเงิน) ถ้าวันหน้าแก้ราคาขายหรืออัตรา ยอดที่จ่ายไปต้องไม่เปลี่ยนตาม เหตุผลเดียวกับ `order_item.unit_price` ในสัปดาห์ที่ 3
- **ไม่เก็บค่าที่คำนวณได้อื่น ๆ** เช่น ยอดใช้งบสะสมใน `budget_allocation` หรือยอดรวมบรรทัดใน `purchase_order_item` เพราะจะเกิดความไม่สอดคล้องเมื่อข้อมูลต้นทางเปลี่ยน

### 4.4 ระดับ BCNF — ตัวกำหนดทุกตัวต้องเป็นซูเปอร์คีย์

ตรวจ FD ของทุกตารางแล้ว ตัวกำหนดที่ไม่ใช่คีย์หลักมีเฉพาะคีย์คู่แข่งซึ่งเป็นซูเปอร์คีย์อยู่แล้ว จึงผ่าน BCNF ทั้งหมด ตัวอย่าง

| ตาราง | FD ที่ตรวจ | ผล |
|---|---|---|
| `expense_category` | `category_code → category_id, category_name, cost_type` | `category_code` เป็นคีย์คู่แข่ง (UNIQUE) จึงเป็นซูเปอร์คีย์ → ผ่าน |
| `budget_period` | `(fiscal_year, quarter) → period_id, start_date, end_date` | ประกาศ UNIQUE ไว้แล้ว → ผ่าน |
| `budget_allocation` | `(branch_id, period_id, category_id) → amount_allocated` | ประกาศ UNIQUE ไว้แล้ว → ผ่าน |
| `vehicle_unit` | `vin → unit_id, model_id, color` | `vin` เป็นคีย์คู่แข่ง (UNIQUE) → ผ่าน |
| `customer_phone` | `(customer_id, phone_no) → phone_type, is_primary` | ตัวกำหนดคือ PK ทั้งชุด → ผ่าน (v2) |

**ไม่มีการลดรูปบรรทัดฐาน (denormalize)** ในรอบนี้ เพราะปริมาณข้อมูลยังไม่มีเหตุผลด้านประสิทธิภาพมารองรับ

## ภาคผนวก v2 — แก้ตามข้อเสนอแนะตอนนำเสนอความคืบหน้า

**ข้อเสนอแนะจากอาจารย์:** ลูกค้าหนึ่งคนมีเบอร์โทรได้หลายเบอร์ จึงต้องออกแบบเบอร์โทรเป็นแอตทริบิวต์พหุค่า (multivalued)

**ปัญหาของแบบเดิม:** `customer.phone varchar(20) UNIQUE` เก็บได้เบอร์เดียว ถ้าจะเก็บหลายเบอร์ต้องคั่นจุลภาคในช่องเดียว (ละเมิด 1NF ค้นหาเบอร์เดียวไม่ได้) หรือทำ `phone1..phone3` (เบอร์ที่ 4 เก็บไม่ได้ ค้นต้อง OR หลายชั้น)

**การแก้ (กฎแปลงข้อ 6 — แอตทริบิวต์พหุค่า → ตารางใหม่ + FK กลับหาเจ้าของ):**

| ตาราง | คอลัมน์ | ข้อกำหนด |
|---|---|---|
| `customer_phone` | `customer_id` | FK → customer, `ON DELETE CASCADE` (เบอร์ไม่มีความหมายถ้าไม่มีเจ้าของ) |
| | `phone_no` | PK ผสม `(customer_id, phone_no)` · `CHECK` รูปแบบ `^0[0-9]{8,9}$` |
| | `phone_type` | `CHECK IN ('MOBILE','HOME','WORK')` |
| | `is_primary` | partial unique index → เบอร์หลักได้ 1 เบอร์ต่อลูกค้า |

- ความสัมพันธ์ customer → customer_phone เป็น 1:M แบบ (1,N) — ลูกค้าต้องมีอย่างน้อย 1 เบอร์
- กฎ (1,N) ฝั่ง "หลาย" SQL ธรรมดาบังคับไม่ได้ (ตอน INSERT ลูกค้ายังไม่มีเบอร์) → บังคับที่ backend: เพิ่ม/แก้ลูกค้าและเบอร์ใน transaction เดียว ถ้าไม่มีเบอร์จะไม่บันทึก
- ตัดคอลัมน์ `customer.phone` ออก · จำนวนตารางเพิ่มจาก 14 เป็น 15
- FD: `(customer_id, phone_no) → phone_type, is_primary` — ตารางอยู่ใน 3NF/BCNF
