# CE396 — ระบบบริหารงบประมาณการจัดซื้อ ค่านายหน้า และค่าใช้จ่ายแฝง

ฐานข้อมูลสำหรับตัวแทนจำหน่ายรถจักรยานยนต์ (PostgreSQL schema `moto_budget`, 15 ตาราง)
พร้อมเว็บสาธิต: หน้ารันคำสั่งสืบค้น 5 ข้อ และหน้าจัดการลูกค้าที่มีเบอร์โทรได้หลายเบอร์

## โครงสร้าง

```
erd/        แผนภาพ ER — erd.png + erd.mmd (v2 ล่าสุด, ต้นฉบับแก้ได้) · erd-v1.png (ฉบับก่อนเพิ่ม customer_phone)
sql/        01-ddl.sql · 02-sample-data.sql (ทุกตาราง ≥ 10 แถว) · 03-business-queries.sql · 04-verify.sql
docs/       er-design.md — เหตุผลการออกแบบ + ภาคผนวก v2 (multivalued)
slides/     สไลด์นำเสนอ
backend/    Express + pg — API
public/     หน้าเว็บ HTML/CSS/JS (ไม่มี build step)
scripts/    setup-db.js — สร้างฐานข้อมูลและโหลดข้อมูล
```

## วิธีรัน (ต้องมี PostgreSQL 16+ และ Node.js 20+)

1. ติดตั้งแพ็กเกจ
   ```bash
   npm install
   ```
2. คัดลอก `.env.example` เป็น `.env` แล้วใส่รหัสผ่าน postgres ของเครื่องตัวเองที่ `PGPASSWORD`
3. สร้างฐานข้อมูล `ChickenRacing` + ตาราง + ข้อมูลตัวอย่าง (รันซ้ำได้ ข้อมูลกลับเป็นค่าตั้งต้น)
   ```bash
   npm run db:setup
   ```
4. เปิดเว็บ แล้วเข้า http://localhost:3000 (ถ้าเพื่อนเปิดจากเครื่องอื่นในวงแลนเดียวกัน ใช้ IP ของเครื่องนี้แทน localhost)
   ```bash
   npm start
   ```

ถ้าจะรันใน pgAdmin แทน: สร้างฐานข้อมูลเอง แล้วเปิด Query Tool รัน `sql/01` → `sql/02` → `sql/03` → `sql/04` ตามลำดับ
(`04-verify.sql` ตรวจงานตัวเองและทดลองละเมิดข้อกำหนด 5 แบบ — ดูผลในแท็บ Messages)

กฎธุรกิจที่ระบบบังคับ (ลองทำผิดให้ดูตอนนำเสนอได้):
- ใบสั่งซื้อใหม่ต้องไม่เกินงบจัดซื้อคงเหลือของสาขา/รอบงบนั้น วันที่ต้องอยู่ในรอบงบที่เปิดอยู่ · ล็อกบรรทัดงบด้วย `SELECT ... FOR UPDATE` กันบันทึกพร้อมกันจนเกินงบ
- สถานะใบสั่งซื้อ: ร่าง → อนุมัติ/ยกเลิก · อนุมัติ → ยกเลิก · รับรถแล้วยกเลิกไม่ได้
- ค่าใช้จ่ายแฝงต้องเป็นหมวดชนิด HIDDEN · หมวดเดียวกันวันเดียวกันซ้ำไม่ได้ (`uq_hidden_unit_cat_date`)
- ค่านายหน้า: ผู้ปิดการขายได้อัตราประจำตัว ผู้ช่วย 1% ผู้แนะนำ 0.5% · หนึ่งดีลมีผู้ปิดการขายคนเดียว · จ่ายแล้วลบไม่ได้

## แก้ตามข้อเสนอแนะ: เบอร์โทรเป็นแอตทริบิวต์พหุค่า

- ตัด `customer.phone` → ตารางใหม่ `customer_phone(customer_id, phone_no, phone_type, is_primary)` PK ผสม, FK `ON DELETE CASCADE`
- เบอร์หลักได้ 1 เบอร์ต่อลูกค้า: `CREATE UNIQUE INDEX ... WHERE is_primary`
- "ลูกค้าต้องมีอย่างน้อย 1 เบอร์" (1,N) SQL บังคับไม่ได้ → backend ตรวจ และบันทึกลูกค้า+เบอร์ใน transaction เดียว (`backend/customers.js`)

## เตรียมตอบคำถามรายบุคคล

- ทำไม customer_phone ใช้ PK ผสม ไม่ใช้ `phone_id serial`? → คู่ (ลูกค้า, เบอร์) ไม่ซ้ำอยู่แล้ว และกันใส่เบอร์เดิมซ้ำให้ลูกค้าคนเดิมโดยอัตโนมัติ
- ทำไม CASCADE? → เบอร์ไม่มีความหมายเมื่อไม่มีเจ้าของ ส่วน `sale → customer` เป็น RESTRICT เพราะการขายเป็นเอกสารทางบัญชี
- ข้อ 3 ทำไมเฉลี่ยใน derived table สองชั้น? → ต้องการค่าเฉลี่ยของ "ยอดรวมรายคน" ไม่ใช่ค่าเฉลี่ยรายดีล (`AVG(SUM())` เขียนตรง ๆ ไม่ได้ → error 42803)
- ข้อ 4 ทำไม LEFT JOIN? → สาขาที่ได้งบแต่ยังไม่สั่งซื้อต้องยังแสดง (ใช้จริง = 0 ผ่าน `COALESCE`)
- ข้อ 5 correlated subquery ทำงานอย่างไร? → รันชั้นในใหม่ทุกแถวของรถ เพื่อรวมค่าใช้จ่ายแฝงของคันนั้น
- ทำไม PK เป็น `serial` ไม่ใช้ `vin` / `tax_id`? → เกณฑ์เลือก PK 3 ข้อ: ไม่เปลี่ยนค่า · สั้นเปรียบเทียบเร็ว · ไม่อ่อนไหว — คีย์ธรรมชาติเก็บไว้เป็น `UNIQUE` (`uq_unit_vin`, `uq_supplier_tax_id`) แทน
- ทำไมเก็บ `commission_amount` ทั้งที่คำนวณได้ (derived)? → เป็นยอดเงินที่จ่ายจริงแล้ว ต้องไม่เปลี่ยนตามราคา/อัตราที่แก้ทีหลัง
- ข้อ 2 AVG มีปัญหากับ NULL ไหม? → `sale_price` เป็น `NOT NULL` จึงไม่มีแถวหลุดจากตัวหาร (AVG ตัด NULL ทั้งตัวตั้งและตัวหาร)
- ทำไมหาลูกค้าที่ไม่มีเบอร์ใช้ `NOT EXISTS` ไม่ใช้ `NOT IN`? → ถ้าชั้นในมี NULL แม้แถวเดียว `NOT IN` ได้ 0 แถวเงียบ ๆ
- 1:1 ระหว่าง `sale` กับ `vehicle_unit` บังคับด้วยอะไร? → `uq_sale_unit_id` (UNIQUE บน FK) — ถ้าไม่มีจะกลายเป็น 1:M ทันที
